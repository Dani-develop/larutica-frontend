## Qué se hizo

y una plantilla local de GitHub Issues:
`.github/ISSUE_TEMPLATE/excepcion-seguridad.yml`. Exige hallazgo vinculado,
alcance/version/commit, evidencia, justificación, mitigaciones, responsable,
revisor distinto, dos aprobaciones humanas verificables y fecha límite.
Si cambia una exigencia académica obligatoria, requiere aprobación del docente.

**No se crearon Issues, no se aprobaron excepciones y no se modificaron controles
para aceptar riesgos.** El registro 7.5 de Axel figura pendiente en la copia local.
No se puede afirmar que todo el equipo tenga cero excepciones abiertas sin
confirmarlo en ese registro. Se mantienen bloqueantes los hallazgos detectados.

Se añadió una consulta reproducible de Issues en modo de solo lectura:

```bash
npm run security:exceptions
npm run test:exceptions
```

La consulta técnica no sustituye la confirmación de Axel: si devuelve cero,
solo describe el repositorio y las convenciones inspeccionadas. Si falla, devuelve
`incompleto`, no cero excepciones. No publica Issues ni aprueba solicitudes.

## Decisiones tomadas

- Conservar una sola ficha por excepción, en el registro único de Axel. No crear un registro JSON/Markdown paralelo ni IDs E-NN inventados.
- La plantilla solicita decisiones humanas, no las suplanta. Pedir una excepción no la vuelve vigente y el agente nunca firma aprobaciones.
- No proponer aceptación masiva de avisos SCA ni supresiones de secretos solo para que el gate pase.
- La clave localhost y AAGUID públicos requieren clasificación, no una declaración automática de riesgo de producción aceptado.
- Ninguna excepción sustituye revocación/rotación real ni ejecución efectiva de controles.
