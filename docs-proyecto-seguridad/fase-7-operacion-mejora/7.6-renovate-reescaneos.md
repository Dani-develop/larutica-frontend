### Reescaneo programado de dependencias

- Lo que existe: [`security.yml`](../../.github/workflows/security.yml) ejecuta OSV-Scanner (junto con Semgrep y Gitleaks) en `pull_request`, `push` a `main`/`development` y `workflow_dispatch`, con las herramientas fijadas por versión y `permissions: contents: read`. El comando de dependencias es `npm run security:deps`.
- **Brecha cerrada el 2026-11-13:** antes ningún workflow definía `schedule`/`cron`. Se llevó a `security.yml` en `main` (directo, por decisión de Frander, sin revisión de CODEOWNER; queda pendiente) lo propuesto en el PR [#56](https://github.com/Dani-develop/larutica-frontend/pull/56): `schedule` con `cron: "0 12 * * 1"` (lunes 12:00 UTC, 06:00 en Costa Rica) y un job `reescaneo-hallazgo` con `issues: write` solo en ese job. Ese job abre o comenta un único Issue «hallazgo candidato» cuando el reescaneo programado o manual falla.
- **Aún no verificado:** la primera ejecución programada sería el lunes 2026-11-16, 12:00 UTC. El job `reescaneo-hallazgo` solo corre si el análisis falla y no se ha ejecutado nunca, así que la creación automática del Issue no está probada. Los workflows `schedule` solo corren sobre la rama predeterminada.
- Ejecución manual: **Actions → Analisis de seguridad (3.2) → Run workflow**, o `gh workflow run security.yml`.

### Cómo un resultado crea o actualiza un hallazgo

Procedimiento vigente (manual, definido por [7.5](7.5-registro-unico-hallazgos.md) y [su procedimiento](../evidencia/7.5-taxonomia-y-procedimiento.md)):

1. Un resultado nuevo puede venir de tres fuentes: (a) un PR de Renovate cuyo check de OSV o de pruebas falla, (b) un reescaneo (manual hoy, programado cuando se fusione la propuesta) cuyo check `Seguridad - Semgrep, Gitleaks y OSV` falla, (c) un aviso de OSV sobre una dependencia que Renovate aún no actualiza.
2. Una persona descarga el artefacto `seguridad-<sha>-<intento>` de esa corrida (14 días de retención) y clasifica cada aviso: confirmado, falso positivo o pendiente.
3. Si el aviso ya tiene un Issue `H-NN`, se **actualiza** ese Issue con la nueva corrida, versión y estado, sin abrir otro. Si no existe, se **crea** un Issue con la plantilla `hallazgo.md` y el siguiente `H-NN`, con paquete, versión afectada, severidad justificada, tratamiento y el PR correctivo.
4. El PR correctivo es el PR de Renovate (si la versión parcheada existe) o un `overrides` en `package.json`, como se hizo en H-06 (`eefdb7d`). Se cambia a `Verificado` solo con una nueva corrida de OSV en CI sobre el SHA corregido.
5. Si no hay corrección posible, el Issue se vincula a una excepción `E-NN` con responsable, justificación y fecha de revisión (ver [5.6](../fase-5-preparacion-version/5.6-excepciones-seguridad.md)).
6. El cierre lo decide una persona con evidencia; nunca lo cierra la automatización.

Con el job `reescaneo-hallazgo` el paso 1(b) crea o comenta automáticamente un Issue titulado «Reescaneo programado: hallazgo candidato (7.6)», que sigue siendo candidato hasta que alguien aplique los pasos 2 a 4 (la automatización no está probada todavía; ver arriba).

Ejemplo real de un resultado que actualizó un hallazgo: H-06 (avisos de dependencias; OSV local de 78 a 0 y `npm audit` en 0) está en [registro-hallazgos](../evidencia/registro-hallazgos.md). La corrida de OSV en CI [43522557908](https://github.com/FranderCT/larutica-frontend-entrega/actions/runs/43522557908) sobre `981b084` dio 0 avisos.

### Cómo reproducirlo

1. Validar la configuración: `npx --yes --package renovate renovate-config-validator renovate.json` (sin salida de error = válida).
2. Consultar los PR de Renovate: `gh pr list --repo Dani-develop/larutica-frontend --state all --search "author:app/renovate"`.
3. Para cada PR citado: `gh pr view <n> --repo Dani-develop/larutica-frontend --json statusCheckRollup,reviews` y comprobar que los tres checks obligatorios están en `SUCCESS` y que hay aprobación de otra persona.
4. Comprobar el `cron`: `grep -n "schedule\|cron" .github/workflows/security.yml`.

## Decisiones tomadas

- Se usa Renovate GitHub App, no un workflow de Actions, para no gestionar tokens o secretos de Renovate en el repositorio.
- El horario es semanal en zona horaria de Costa Rica y la concurrencia se limita a un PR para que cada actualización pase por los checks y por revisión sin acumularse.
- Los PR de Renovate no se fusionan automáticamente: pasan por los mismos checks que cualquier cambio y requieren aprobación humana. Las actualizaciones major llevan la etiqueta `major-update`.
- El escaneo de imagen por digest se descarta porque el proyecto no tiene Dockerfile ni imagen propia.
- Los resultados de escaneo nunca cierran un hallazgo por sí solos: crean o actualizan un Issue candidato y una persona lo clasifica.
