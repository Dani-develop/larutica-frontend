## Los tres flujos

### F-01 Inicio de sesión y acceso por rol

| | |
|---|---|
| **Actor** | Cualquier persona con cuenta: Viajero, Agencia, Transporte o Admin. |
| **Objetivo** | Autenticarse y llegar a la pantalla que corresponde a su rol. |
| **Resultado esperado** | Se crea una sesión opaca (cookie `HttpOnly`, vence a los 30 min de inactividad o a las 8 h absolutas) y se redirige a un destino permitido para el rol. |
| **Por qué es crítico** | Maneja credenciales, sesiones y el rol que decide quién llega a pagos, liquidaciones y usuarios. Un fallo permite tomar cuentas o escalar privilegios (acceso al panel Admin). |

Criterios de aceptación:

| ID | Tipo | Dado / Cuando / Entonces |
|---|---|---|
| F01-C1 | Éxito | **Dado** una cuenta Admin activa, **cuando** envía correo y contraseña válidos, **entonces** se crea la sesión y llega a `/dashboard`. |
| F01-C2 | Éxito | **Dado** una cuenta Viajero que llegó desde una experiencia (`?next=/experiencias/...`), **cuando** inicia sesión, **entonces** vuelve a esa experiencia con su selección. |
| F01-E1 | Error | **Dado** una contraseña incorrecta, **cuando** intenta iniciar sesión, **entonces** la API responde 401 con un mensaje genérico, sigue en `/login` y no se crea sesión. |
| F01-A1 | Uso indebido | **Dado** un enlace de inicio de sesión con `next=https://evil.invalid/`, **cuando** la persona se autentica, **entonces** se ignora el destino externo y va a `/dashboard` (sin redirección abierta). |
| F01-C3 | Éxito | **Dado** una cuenta Agencia que llegó desde una experiencia, **cuando** inicia sesión, **entonces** vuelve a esa experiencia: todos los roles pueden comprar a su nombre (`docs/flujo-reservas.md`). |
| F01-A2 | Uso indebido | **Dado** un `next` con doble barra (`//evil.invalid/ruta`), **cuando** la persona se autentica, **entonces** se ignora y va a `/dashboard`. |
| F01-A3 | Uso indebido | **Dado** una solicitud sin sesión (o con sesión vencida), **cuando** pide un recurso protegido de la API, **entonces** recibe 401 y no se devuelve ningún dato. *(Se comprueba a fondo en 4.5.)* |

### F-02 Compra y pago de una reserva

| | |
|---|---|
| **Actor** | Persona con cuenta (cualquier rol puede comprar *a su nombre*); caso principal: Viajero. |
| **Objetivo** | Reservar una salida de una experiencia aprobada pagando con tarjeta mediante Onvo. |
| **Resultado esperado** | Se crea una reserva `CONFIRMED` solo después de un cobro verificado por el servidor (estado, importe y moneda). Antes del cobro solo existe un intento (`reservation_checkouts`) que retiene cupos hasta 15 minutos. |
| **Por qué es crítico** | Maneja dinero y datos del pasajero. Un fallo causa cobros sin reserva, reservas sin cobro, sobreventa de cupos o cobros duplicados. Los datos de tarjeta nunca pasan por el backend: los captura el SDK de Onvo. |

| ID | Tipo | Dado / Cuando / Entonces |
|---|---|---|
| F02-C1 | Éxito | **Dado** una salida futura con cupo, **cuando** el viajero elige personas, continúa al pago y paga, **entonces** se crea una reserva `CONFIRMED` y no existía antes del cobro. |
| F02-E1 | Error | **Dado** una tarjeta rechazada, **cuando** el viajero intenta pagar, **entonces** ve una alerta, no se crea reserva y puede reintentar el mismo checkout sin duplicar reservas ni cobros. *(No se exige el mismo ID de intento de Onvo: `lib/payments/checkout.ts` reutiliza el intento si sigue pendiente, pero puede crear otro si el anterior quedó fallido.)* |
| F02-E2 | Error | **Dado** un intento vencido (más de 15 min), **cuando** el viajero comprueba el estado, **entonces** ve que terminó, no se crea reserva y puede consultar disponibilidad de nuevo. |
| F02-A1 | Uso indebido | **Dado** una solicitud de compra con `passengerId` de otra persona, cantidad `0` o negativa, o campos extra, **cuando** llega a `POST /api/checkouts`, **entonces** responde 400, no crea intento y el precio sale del servidor, nunca del cliente. |
| F02-A2 | Uso indebido | **Dado** un intento cancelado mientras la persona está en el formulario de pago, **cuando** el cobro se completa, **entonces** nunca se muestra «Reserva realizada», no hay reserva y se solicita la devolución. |
| F02-A3 | Uso indebido | **Dado** una solicitud sin sesión, **cuando** intenta crear un intento de compra, **entonces** recibe 401. |

### F-03 Consulta y cancelación de reservas

| | |
|---|---|
| **Actor** | Viajero (sus reservas), Agencia o Transporte (reservas de sus publicaciones) y Admin (todas). |
| **Objetivo** | Ver las reservas dentro del ámbito propio y cancelar antes de la salida. |
| **Resultado esperado** | Cada rol ve solo su ámbito. Cancelar antes de la salida pasa la reserva a `CANCELLED`, libera cupos y solicita la devolución; la cancelación se conserva aunque falle el proveedor de pagos. |
| **Por qué es crítico** | Expone datos personales de pasajeros (nombre, contacto) y mueve dinero (devoluciones). Un fallo de permisos muestra o cancela reservas ajenas. |

| ID | Tipo | Dado / Cuando / Entonces |
|---|---|---|
| F03-C1 | Éxito | **Dado** una reserva pagada en una publicación de la agencia, **cuando** la agencia abre su panel de reservas, **entonces** la ve sin filtros adicionales y sin opción de «Confirmar reserva». |
| F03-C2 | Éxito | **Dado** un viajero con una reserva `CONFIRMED` y salida futura, **cuando** la cancela, **entonces** pasa a `CANCELLED`, se liberan los cupos y se solicita la devolución. |
| F03-E1 | Error | **Dado** una reserva cuya salida ya comenzó o que ya está cancelada, **cuando** se intenta cancelar, **entonces** la API responde 400 y el estado no cambia. |
| F03-A1 | Uso indebido | **Dado** un viajero que no es el pasajero, **cuando** consulta o cancela por ID una reserva ajena, **entonces** recibe 404 o 403, sin datos ni cambios. |
| F03-A2 | Uso indebido | **Dado** una agencia que no organiza la experiencia **y que tampoco es la pasajera**, **cuando** intenta ver o cancelar esa reserva, **entonces** se rechaza igual que en F03-A1. *(Una cuenta Agencia sí puede ver y cancelar una reserva comprada a su propio nombre: `canReadReservation` y `assertKnownActor` la tratan como pasajera.)* |
| F03-A3 | Uso indebido | **Dado** una persona sin sesión, **cuando** abre «Mis reservas» o llama a la API, **entonces** la interfaz la lleva a iniciar sesión y la API responde 401. |

## Decisiones tomadas

- **Tres flujos, no más.** Se eligieron los que mueven credenciales (F-01), dinero (F-02) y datos personales con devoluciones (F-03). Quedan fuera pagos a agencias/liquidaciones y publicaciones, que también son sensibles pero requieren rol Admin o Agencia y encajan mejor como ampliación.
- **Reglas «observadas», no «aprobadas».** Se documentó lo que hace el código y se separó lo que falta decidir en Q-01 a Q-03 en lugar de suponer la respuesta.

## Resultados

- Los 19 criterios tienen prueba: F-01, F-02 y F-03 en E2E (4.4) y F01-A3, F03-A2, Q-02 y Q-03 en autorización (4.5). En Actions (run 43443732592, commit `9df333c`) pasan las 19 pruebas E2E y las 8 de autorización.
- La revisión técnica de Daniel Núñez encontró tres defectos de la ficha (F02-E1, F03-A2 y el conteo de criterios); los tres están corregidos arriba.
- Q-02 y Q-03 están decididas y probadas. **Q-01 sigue abierta.**
- Las tres casillas de revisión siguen sin marcar: las marca Daniel Núñez al reproducir la evidencia. La aprobación del PR #10 salió de la cuenta `Dani-develop` y no sustituye esa firma.

## Limitaciones y alcance excluido

- Recuperación de contraseña, passkeys y registro quedan fuera de F-01 por tiempo.
- La confirmación 3DS, los webhooks reales y las devoluciones reales de Onvo requieren sandbox y no se cubren (ver `docs/flujo-reservas.md`).
- El criterio F01-A3 (sesión vencida) se prueba solo a nivel de autorización en 4.5.
