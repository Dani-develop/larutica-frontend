Cómo reproducirlo:

```bash
npm ci
npx playwright install chromium   # una sola vez
npm run build:vercel              # genera .vercel/output (lo sirve el harness)
npm run test:e2e                  # arranca la API y la interfaz aisladas y corre las 19 pruebas
npx playwright show-report        # reporte HTML
```

Con `CI=true` Playwright arranca siempre sus propios servidores; en local reutiliza los que ya estén abiertos.

## Decisiones tomadas

- **`@playwright/test` en lugar de ampliar los scripts `*.browser.mjs`.** Esos scripts tienen rutas de Windows fijas y no devuelven reporte; no podrían ser un check de CI portable.
- **El ID del criterio forma parte del nombre de la prueba** (`F02-A2 ...`). Así la trazabilidad de 1.1 se comprueba con una búsqueda de texto.
- **Una prueba que comprueba un rechazo incluye un control positivo.** Ejemplo: en F03-A1 primero se verifica que la persona dueña SÍ ve su reserva (200) y después que otra persona recibe 403/404. Sin el control, un id equivocado también produciría 404.
- **No se cambió una expectativa para que coincidiera con el código a ciegas.** F01-A2 falló al principio: yo había supuesto que una Agencia con un `next` de viajero iba a `/dashboard`, pero la regla documentada en `docs/flujo-reservas.md` dice que todos los roles pueden comprar. Se verificó la regla en la documentación, se corrigió el criterio en 1.1 (nuevo F01-C3) y se agregó una prueba de abuso distinta (`//evil.invalid/`).

## Limitaciones y alcance excluido

- **F-01 usa un servicio de sesión simulado** (`/api/auth/login` y `/api/auth/session`): el inicio de sesión real depende de Supabase Auth y no existe en el ambiente aislado. Se prueban formulario, mensajes y redirección segura, no la verificación de la contraseña ni la cookie `HttpOnly`. La sesión real se cubre parcialmente en `tests/opaque-session.integration.mjs` (requiere Supabase) y en las pruebas de autorización del ítem 4.5.
- **El pago usa el SDK de Onvo simulado** (sin 3DS, webhooks ni devolución real). Ver `docs/flujo-reservas.md`.
- La identidad en las pruebas de API se simula con la cabecera `x-qa-actor` del harness; no prueba que un token de sesión falso sea rechazado.
- F03 no cubre la cancelación con la salida ya iniciada (requeriría controlar el reloj): F03-E1 prueba el caso «ya cancelada».
- No se probó móvil ni accesibilidad de estos flujos aquí (los scripts de `tests/qa/` lo hacen de forma manual).
